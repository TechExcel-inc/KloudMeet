LiveDoc Whiteboard

A white Excalidraw board that the host, co-hosts and presenter can draw on together during a KloudMeet meeting. Everyone else watches the presenter's view. Each board is saved as a LiveDoc document in Kloud, so it can be reopened from LiveDoc Space and viewed in the Kloud web app.

Whiteboard stage

  • When the current LiveDoc file is a whiteboard, KloudMeet shows the Excalidraw canvas in the stage area. The LiveDoc iframe stays mounted underneath, so the document list, file switching and following work as they do now.
  • The Excalidraw canvas is white (theme: "light"). Excalidraw's own main menu, library and help are hidden. Editors get a compact dark toolbar in KloudMeet style: select, hand, pen, shapes, arrow, text, eraser, undo/redo and zoom.
  • Editors see each other's cursors with name labels. Viewers see the presenter's cursor.
  • A small status chip shows Saved, Saving… or Offline, changes kept locally.

KloudMeet does not call the Java server from the browser. It goes through its own API routes, using the same upstream helpers it already uses (lib/peertimeUpstream.ts → buildMeetingServerUrl). This keeps tokens and CORS in one place.

Document model

Whiteboard document type

A whiteboard is a normal Kloud document (Document plus LessonDocument) with a new FileTypeEnum.WHITEBOARD. Today we spot boards by checking for excalidraw.kloud.cn in the URL; the new file type replaces that check. Its AttachmentUrl is a fixed marker, kloud-whiteboard://{attachmentId}, so older clients that only know URLs don't try to load a web page.

New table whiteboard_scene

ColumnTypeNotes
attachment_idINT, PKThe whiteboard document
versionINTGoes up by 1 on each save. Used for optimistic locking
sceneLONGTEXTExcalidraw scene JSON: {type, version, elements, appState: {viewBackgroundColor, gridSize}}. Deleted elements are removed before saving
text_contentTEXTText from text elements and labels, in reading order. Used by search and Doc AI
preview_urlVARCHAR(512)PNG made on save. Thumbnail in Space and fallback view
element_countINTFor quick checks and logs
updated_by / updated_timeINT / DATETIME
create_by / create_timeINT / DATETIME

Size: a busy board with 2,000 elements is about 1–2 MB of JSON, so LONGTEXT is enough. Image files are not stored in the scene in Phase 1 (the image tool is off).

Server API

New controller WhiteboardController at /whiteboard in kloud-meeting. It follows ExcalidrawController: @AuthenticateToken, ResultVO responses, and the controller/service/mapper split.

MethodPathBody / queryReturns
POST/whiteboard/create{lessonId, title?}{attachmentId, itemId, title}. Creates the Document, LessonDocument and an empty scene at version 0. Same flow as addHtmlDefaultPage
GET/whiteboard/scene?attachmentId{version, scene, updatedTime}
POST/whiteboard/scene{attachmentId, baseVersion, scene, textContent}{version}. Returns VERSION_CONFLICT with the current version if baseVersion is out of date
POST/whiteboard/previewmultipart: attachmentId, version, file (PNG){previewUrl}. Also used as the document thumbnail

Permission check on save: in Phase 1 the user must be signed in and a member of the lesson. In Phase 2 the server also checks that the user is host, co-host or presenter of the live meeting. The LiveKit receivers already enforce this for live strokes.

Creating from the panel: the White Board button calls POST /api/whiteboard/create in KloudMeet, then asks the LiveDoc iframe to refresh its file list and switch to the new file. Today this is runAction('document.addBlank'); we add an action such as document.openById to MainStage.

Live sync

A new LiveKit data topic wb, alongside the existing anno, rc and ctl. Every message has {t, board, from}, where board is the AttachmentID.

Type tSent byDeliveryPayload and rule
elEditorsReliable, at most every 50 ms{elements[]}: only elements whose version went up since the last send. Receivers merge with reconcileElements and apply with captureUpdate: NEVER, so a person's undo only covers their own changes
ptrEditorsLossy, about 30 ms{x, y, tool, down} in scene coordinates, shown as collaborator cursors
viewPresenterLossy while moving, reliable when stopped{x, y, w, h}: the visible scene area. Viewers fit this area to their own screen
reqAnyone joiningReliable{haveVersion}: "send me anything newer than this saved version"
fullElected saverLiveKit text stream (sendText, topic wb-bulk)The full current scene. Used for req and for any el batch over ~12 KB
savedElected saverReliable{version} so others can show "Saved"

Role check on receive: each client ignores el and ptr from a sender whose current role is not host, co-host or presenter. It uses the same role data that resolveLiveDocEmbedRole uses. A change made in a hacked browser therefore never reaches anyone else's canvas.

  • Whose view is followed: the presenter's. If there is no presenter, the host's. If the host is away, the first co-host's.
  • Different screen sizes: the presenter sends the visible scene area, not scroll and zoom values. Each viewer picks the zoom that fits that area in their own stage. A laptop and a 4K monitor show the same content at different scales.
  • Role changes during the meeting switch the canvas between edit and view mode immediately (viewModeEnabled). Anything the person was drawing is finished and sent first.
  • The Enable Annotation toggle does not affect whiteboards. Whiteboard rights come only from the person's role.

Saving

One saver

The save endpoint overwrites the whole scene, so only one client saves. Every client chooses the same saver from the room's current participants: the presenter, else the host, else the co-host with the lowest identity. If the saver leaves, the next one in that order takes over. No messages are needed to decide this.

When it saves

  • After 2 s with no changes, and at least every 10 s while people keep drawing.
  • When the meeting switches to another file, when the saver leaves, and when the meeting ends.
  • Each save sends the scene and the text. Every 3rd save, and always the last one, also sends a new PNG preview from exportToBlob (max 1600 px wide).

Conflicts and failures

  • If the server returns VERSION_CONFLICT (for example a stale saver after a network split), the saver loads the server scene, merges it with reconcileElements and saves again.
  • If a save fails, the saver keeps the scene in IndexedDB under the board ID and retries with backoff. The status chip shows Offline, changes kept locally.
  • Editors who are not the saver also keep a local copy, so nothing is lost if the saver's browser crashes. The new saver picks it up through req/full.

Kloud-Web viewer

  • Recognize the type. MainStage.vue sets IsWhiteboard: true and sends FileType in onkloudswitchfile for the new type. KloudMeet already reads this into isWhiteboardDoc.
  • Inside KloudMeet (FromJitsi), Kloud-Web shows an empty stage for whiteboard files, because KloudMeet draws the board on top. This avoids loading Excalidraw twice.
  • In the Kloud web app and LiveDoc Space, a read-only viewer built from src/components/excalidraw/index.vue with viewModeEnabled loads GET /whiteboard/scene. While the scene loads or if it fails, the PNG preview is shown.
  • Excalidraw version. Kloud-Web's bundled UMD build in static/excalidraw/ is older than 0.18. We replace it with the 0.18 UMD build so scenes with fractional z-order indexes load correctly.

Risks

  • Recording. LiveDoc Full recording records Kloud-Web, which only sees the board at each save. Until Phase 3 a recording shows the board only as it was at each save, not stroke by stroke.
  • Same-text edits. Two editors typing in the same text box at once: the later version wins for that box. This is acceptable for a whiteboard.
  • Bundle size. Excalidraw adds about 1–2 MB. It loads only when a whiteboard opens (next/dynamic, ssr: false), with fonts and assets served by KloudMeet, not a public CDN.
  • Data channel limits. A large paste can exceed one reliable data packet. Batches over ~12 KB go through LiveKit text streams.
  • Mobile. Viewing works on phones. Drawing on phones is supported by Excalidraw but not a Phase 1 goal.

Open questions

  1. What goes under More? The proposal is From Files (favorites), Paste link and Design link.
  2. Does a document created in a meeting appear in the creator's LiveDoc Space automatically, or does it need an explicit "Save to Space"? This decides whether /whiteboard/create also adds a Space entry.
  3. Where are preview PNGs stored: the same storage as other document thumbnails?
  4. Default board title: "Whiteboard · 2026-11-03 14:30", or the meeting name plus a number?
  5. Should guests (not signed in to Kloud) who become presenter be able to draw? They can draw live, but saving depends on a signed-in saver being in the room.
