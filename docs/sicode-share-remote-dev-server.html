Share Remote Dev Server

2026-10-26Repo: TechExcel-inc/SiCodeStatus: proposal, no code yet

Goal

A developer works in SiCode on a Mac, while the code lives, builds and runs on a remote dev computer, such as the Windows machine that P1's .NET backend needs. The team registers that computer once in EAD Pilot; everyone allowed to use it sees it in SiCode and opens its projects as remote projects.

Short answer Yes, the approach works. SiCode already separates the app from the server that does the work, and it already has a placeholder ssh server type. The missing parts are: opening the SSH connection, starting SiCode's server on the remote computer, tunnelling to it, and an EAD Pilot list of shared dev computers.

This is the same model the Claude desktop app (SSH environments) and VS Code Remote-SSH use: the agent and the tools run on the remote computer, and only the window runs locally.

How it works

SiCode on the Mac opens one SSH connection to the dev computer with the user's own key, starts (or finds) a SiCode server there bound to localhost, and forwards a local port to it through the SSH connection. The app then uses that server exactly like its local one.

EAD Pilot: register and share

An admin registers each dev computer once in EAD Pilot. Pilot shares the computer's details and who may use it, never a password.

In SiCode, a signed-in user then sees a Remote dev servers section in the server picker, with the computers shared with them. Choosing a product in the EAD map can open its folder on the right computer.

Connecting, step by step

  1. List. SiCode loads the user's dev servers from EAD Pilot (new API next to loadProducts).
  2. SSH in. The desktop app (main process) opens SSH with the user's private key, checking the host key against the fingerprint EAD recorded.
  3. Install or update the server. SiCode checks for its server in %LOCALAPPDATA%\SiCode\server\<version>; if the version doesn't match the app, it uploads the matching build over the same connection.
  4. Start or reuse. If this user's server is already running, reuse it; otherwise start it detached so it survives a dropped connection, with a fresh random password and --hostname 127.0.0.1 --port 0. It writes its port to a state file in the user's profile.
  5. Tunnel. Forward a free local port on the Mac to that remote port through the SSH connection.
  6. Check health. Call /global/health through the tunnel, as the local sidecar does today.
  7. Add the server. Register an ssh connection (host plus the tunnel URL and password) in the server list and make it active.
  8. Open projects. The user picks folders on the dev computer, or opens the product folders from EAD. They are stored as that server's projects.

If the connection drops, health polling notices; SiCode reconnects, re-forwards the port and reuses the running server, so sessions continue.

Windows dev computers

  • OpenSSH Server is a built-in Windows feature; it must be on, with the sshd service set to start automatically.
  • Keys for administrators are read from C:\ProgramData\ssh\administrators_authorized_keys; for other accounts, from the user's .ssh\authorized_keys. Non-admin accounts are better.
  • Tools on PATH for the account: git, the .NET SDK or MSBuild (Visual Studio Build Tools for .NET Framework projects), and Node for Vue front ends.
  • Keeping the server running: start it as a detached process (or a per-user scheduled task), so closing the SSH connection doesn't stop it.
  • Shell: the agent's shell commands run in PowerShell on Windows; prompts and tools must expect Windows paths.

Several people, one computer

OptionHowTrade-off
One Windows account per developer (recommended)Each person signs in as themself; each gets their own SiCode server, settings and checkouts.Clean separation and auditing; an admin creates the accounts.
Shared account, separate foldersOne account; SiCode keeps one server per EAD user (own state folder and port) and a git worktree per person or task.Less setup, but everyone can read everyone's files, and the shared password problem returns.

Either way, two people never work in the same checkout. Builds that write to shared folders (IIS sites, shared databases) still need team rules.

Security

  • No shared administrator password, in EAD or anywhere else. Each person uses their own SSH key; EAD stores only public keys and fingerprints.
  • The SiCode server listens on 127.0.0.1 only, with a random password per start. Only the SSH tunnel can reach it.
  • The host key is pinned when the computer is registered, which protects against connecting to an impostor.
  • Removing a member in EAD removes their key from the computer (phase 3) and hides the server in SiCode at once.
  • The private key stays on the developer's Mac, in the macOS Keychain or ~/.ssh, never in EAD.
Before starting Administrator passwords for the P1 servers were pasted into a chat during this discussion. Change them, and move to per-person SSH keys as above.

Phases

Phase 1

Remote server in SiCode

A user adds an SSH server by hand (host, port, user, key). SiCode installs, starts and tunnels to its server, and opens remote projects.

  • Proven on the P1 Windows dev computer
  • No EAD changes
Phase 2

Share through EAD Pilot

Admins register dev computers and members in Pilot; SiCode lists them for each user, and links EAD products to folders on them.

  • EAD backend and Pilot screens
  • Host key pinning from the registry
Phase 3

Keys and access, automated

A small service on each dev computer syncs authorized keys from EAD, so adding or removing a member takes effect without anyone logging in to the computer.

  • Revoke in one place
  • Audit of who connected

Open questions

  1. Who builds the EAD backend part (registry, members, keys), and on which EAD release?
  2. One Windows account per developer, or one shared account with separate folders?
  3. Is P1's backend modern .NET (which also builds on a Mac) or .NET Framework (Windows only)? This decides how much work must run remotely.
  4. Should a dev computer also be usable from SiCode on Windows desktops, not only Macs? The design allows it; it needs testing.
  5. Does any project need the remote computer's GUI (Visual Studio debugging, IIS Manager)? Those still need Remote Desktop alongside SiCode.
